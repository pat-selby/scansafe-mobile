# ScanSafe

Cross-platform QR phishing detection. Checks where a QR code really goes before you open
it, entirely on your phone.

Built with Flutter for iOS and Android. Part of ongoing cybersecurity research in the
AIoT Lab at Grambling State University.

## Status

**36 of 52 roadmap tasks complete.** Phases 0 and 1 are done and verified; Phase 2
(camera + OpenCV decode) has shipped for the web; the native decoder is next.

| Layer | What it does | Status |
|---|---|---|
| 1–3 | Camera, OpenCV pipeline, QR decode | **Done on web** (OpenCV.js); native is TASK-052 |
| 4 | 22-rule URL risk scoring | **Done**, parity-verified |
| 5 | Verdict + dual-layer findings | **Done** |
| 6 | Local scan history | **Done** |
| 7 | Agentic investigation | Out of scope for this release |

What works today: **scan a QR code with the camera** (web build), or paste a link, and get
a SAFE / SUSPICIOUS / HIGH RISK verdict with plain-English reasoning and technical detail
behind a toggle, saved to local history that never leaves the device.

Camera scanning currently runs on the **web build only**, decoding with the OpenCV.js WASM
build. Native Android and iOS still show the scan button disabled — `dartcv4` is TASK-052.
The web path exists because it is the only way onto an iPhone without Mac access; it decodes
identically to the Python prototype on all five QR fixtures (see `docs/evaluation.md`).

## The parity contract

`test/url_scorer_test.dart` holds 41 cases whose expected scores were generated by
running the original Python prototype (`scansafe_prototype.py`). Those are the numbers the
published evaluation was produced with.

A failure there means this engine has drifted from the research artefact — **fix the
engine, don't regenerate the corpus to make the test pass.** Regenerate deliberately, with
`tool/generate_parity_corpus.py`, and document the divergence.

Two ports needed care and are worth knowing about before touching them:

- **`lib/core/parsed_url.dart`** reimplements Python's `urlparse` rather than using Dart's
  `Uri`, which lowercases hosts, strips ports from the authority, and re-encodes paths —
  each of which silently changes a rule outcome.
- **`lib/core/fuzzy.dart`** uses `BigInt` for the 64-bit SimHash because Dart's `int` is
  32-bit for bitwise operations when compiled to JavaScript.

## Layout

```
lib/core/     Layer 4 + decoder interface. Pure Dart — no Flutter imports, no I/O.
lib/data/     Layer 6 — on-device scan history.
lib/ui/       Layer 5 — theme, screens, widgets. All values come from docs/design.md.
test/         Parity corpus, widget tests, accessibility tests.
tool/         Parity corpus generators (Python).
docs/         BuilderOS documents — see below.
```

## Measured behaviour

Full numbers in `docs/evaluation.md`.

| Metric | Value |
|---|---|
| False positives, 212 legitimate URLs | 5 (2.4%) — was 4.2% before TASK-038 |
| Malicious flagged, 25-URL corpus | 23 (92.0%) |
| Malicious rated HIGH RISK | 14 (56.0%) |

**TASK-038 is fixed.** `grambling.edu` scored SUSPICIOUS because `gram` was in the brand
list, redundant with `grambling` and a substring of it. Removing it halved the
false-positive rate and changed no malicious score.

Still open (**TASK-051**): five real URLs — `outlook.office.com`,
`login.microsoftonline.com`, `onedrive.live.com`, `gsumail.grambling.edu` — score
SUSPICIOUS because Rule 8 flags a brand on an apex it doesn't match, which is exactly what
big organisations legitimately do. Fixing it is a research decision, not a patch.

## Privacy

Layers 4–6 make zero network calls. History is on-device only: no accounts, no sync, no
analytics. `url_launcher` is deliberately absent from the dependency tree so an "open
anyway" button cannot be added by accident — the app explains links, it never opens them.
