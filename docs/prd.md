## 1. Overview

### Product Summary

ScanSafe is a cross-platform mobile app that decodes a QR code with OpenCV and scores the
embedded URL against 22 deterministic phishing rules — entirely on-device, with no
network calls in the scan path. It returns a SAFE / SUSPICIOUS / HIGH RISK verdict with
plain-English reasoning and technical detail on demand.

### Objective

Ship a free, production-quality Android and iOS app implementing Layers 1–6 of the
ScanSafe architecture, with the rule engine provably identical to the Python research
prototype that produced the published evaluation numbers.

### Market Differentiation

Built-in camera scanners open links with no check. Third-party scanners upload scanned
URLs. Browser safe-browsing only acts after navigation. ScanSafe is the only option that
checks before navigation, without a network, and shows its reasoning.

### Magic Moment

The phone is pointed at a QR code on a flyer and, before any page can load, the screen
reads HIGH RISK — naming the brand the domain is impersonating.

### Success Criteria

1. Parity corpus passes 100% against the Python prototype.
2. Decode-to-verdict under 500ms on mid-range Android hardware.
3. Zero network calls in the scan path, verifiable by inspection.
4. False-positive rate on a legitimate-domain corpus measured and under 5%.
5. Shipped free on Google Play and the App Store.

## 2. Technical Architecture

### Architecture Overview

```
Camera frames (Layer 1)
        ↓
OpenCV preprocess: BT.601 grey → 5×5 Gaussian → Canny 50/150 → contours (Layer 2)
        ↓
OpenCV QRCodeDetector, 4-stage fallback (Layer 3)
        ↓
UrlScorer — 22 additive rules, pure function, no I/O (Layer 4)
        ↓
Verdict + dual-layer findings (Layer 5)
        ↓
ScanHistoryStore — on-device, 50-item cap (Layer 6)
```

Layers 4–6 are pure Dart with no plugin dependency, so they run identically on Android,
iOS, web, and in unit tests. Layers 1–3 are the only platform-bound code, and they sit
behind the `QrDecoder` interface so the app never depends on a specific decoder.

### Chosen Stack

| Concern | Choice | Rationale |
|---|---|---|
| Framework | Flutter (Dart), stable channel | One codebase for iOS + Android; the rule engine is written once |
| CV / QR decode | OpenCV via a Flutter binding | **Research constraint** — OpenCV must do all computer vision |
| Camera | `camera` plugin | Frame streaming for live decode; well-maintained, both platforms |
| Local storage | `shared_preferences` | A 50-item cap does not justify a database |
| Permissions | `permission_handler` | Consistent camera-permission states across platforms |
| Backend | None | A backend would break the core privacy claim |
| Auth | None | No accounts means nothing to breach |
| Payments | None | Free app |
| Analytics | None | Telemetry contradicts "nothing leaves the device" |
| Crash reporting | Sentry | Required for a responsible public release; scan content never attached |

**These choices are final.** Do not substitute `mobile_scanner`, ML Kit, ZXing, or any
other decoder for OpenCV — that is a stated research constraint, not a preference. Do not
add a state-management package; the app has three screens and `setState` is sufficient.

### Stack Integration Guide

**OpenCV.** Bind through a package exposing `cv::QRCodeDetector`. The decoder must
implement the prototype's four-stage fallback in order, because single-stage decoding
failed on real samples: (1) original colour frame, (2) BT.601 greyscale, (3) Otsu
binarisation for coloured or branded codes, (4) inverted Otsu for light-on-dark codes.
Stop at the first stage that returns a payload.

**Camera.** Stream frames, throttle decode attempts to roughly 4–6 per second to protect
battery, and stop the stream the instant a payload decodes. Never write frames to disk.

**Sentry.** Initialise with `beforeSend` stripping any breadcrumb or extra that could
contain a URL. Scanned payloads, scan history, and decoded text must never reach a crash
report. This is the single network call in the app and must be disclosed in the privacy
policy.


`lib/core/` must not import `package:flutter/*`. That is what keeps the engine testable,
portable, and honest about having no I/O.

### Infrastructure & Deployment

No servers. Android ships as an AAB through Google Play; iOS ships through App Store
Connect. Release builds are produced locally. Signing keys and the Sentry DSN are supplied
via `--dart-define` and never committed.

### Security Considerations

1. **No network in the scan path.** Enforced by keeping `lib/core/` free of HTTP clients.
2. **Scanned URLs are untrusted data.** A decoded payload is never executed, never opened,
   and never used to construct a request. It is scored and displayed, nothing else.
3. **No `url_launcher`.** The dependency is deliberately absent so an "open anyway" button
   cannot be added by accident.
4. **Crash reports are scrubbed.** No URL, payload, or history entry may reach Sentry.
5. **Minimum permissions.** Camera only. No storage, location, contacts, or network
   permission is requested on Android beyond what Sentry requires.
6. **Rule 13 recursion is depth-capped** so a redirect wrapper pointing at itself cannot
   hang the scorer.

### Cost Estimate

$0/month infrastructure. One-time: $25 Google Play registration, $99/year Apple Developer
Program. Sentry's free tier covers expected volume.

## 3. Data Model

No database. Two persisted structures, serialised to JSON in `shared_preferences`.

### Entity Definitions

**ScanResult** — one scored URL.

| Field | Type | Notes |
|---|---|---|
| `url` | String | The payload as decoded, never normalised for display |
| `score` | int | Sum of fired rule weights |
| `level` | RiskLevel | Derived: 0–2 safe, 3–5 suspicious, 6+ high risk |
| `findings` | List\<Finding\> | Empty means clean |
| `scannedAt` | DateTime | ISO 8601 when serialised |

**Finding** — one fired rule.

| Field | Type | Notes |
|---|---|---|
| `ruleId` | int | 1–22. Rule 19b reports as 19. `0` is the sentinel for non-rule notices |
| `plain` | String | Always-visible plain-English text naming the detected pattern |
| `technical` | String | Detail shown behind "See details" |
| `points` | int | Weight contributed |

**RiskLevel** — enum: `safe` ("SAFE"), `suspicious` ("SUSPICIOUS"), `highRisk` ("HIGH RISK").

### Relationships

`ScanResult` owns its `Finding` list. History is an ordered `List<ScanResult>`, newest
first, capped at 50 — the oldest entry is dropped on overflow.

### Indexes

None. A 50-item list is scanned linearly.

## 4. API Specification

### API Design Philosophy

There is no API and no backend. The one internal contract worth specifying is the scoring
boundary, because everything else depends on it staying pure.

### Endpoints

None. Internal contract instead:

```dart
ScanResult UrlScorer.score(String urlString)
Future<String?> QrDecoder.decode(List<int> imageBytes)
```

`UrlScorer.score` must remain a pure function: no I/O, no clock dependence beyond
stamping `scannedAt`, no global mutable state except the injected `SimHashCache` backing
Rule 20. Given the same input and cache state it must return the same result forever.

## 5. User Stories

**Epic: Scanning a code**
- As a student, I can point my camera at a QR code and get a verdict before any page loads.
- As a student, I can scan in low light using a torch toggle.
- As a student, if the code won't decode, I'm told what to try rather than shown an error code.
- As a student, if I deny camera access, I can still check links by typing them.

**Epic: Understanding a verdict**
- As a student, I see a verdict word, an icon, and a score, so meaning doesn't depend on colour.
- As a student, I read plain-English reasons that name the actual pattern found.
- As a security-aware user, I can expand any finding to see the exact rule and its output.
- As a student, I'm told what the check does *not* cover, so I don't over-trust a SAFE result.

**Epic: Reviewing past scans**
- As a student, I can see my recent scans and reopen any result.
- As a student, I can swipe to delete one scan or clear all of them.
- As a privacy-conscious user, I can confirm my history never leaves the device.

## 7. Non-Functional Requirements

**Performance.** Decode-to-verdict under 500ms on mid-range Android. Scoring itself must
stay under 10ms — it is a pure function over a short string. Camera decode attempts
throttled to 4–6/second. Cold start under 2s.

**Reliability.** Crash-free sessions above 99.5%. A corrupt history blob must never brick
the history screen — it is discarded and the screen renders empty.

**Privacy.** Zero network calls in the scan path. Camera frames never written to disk.
Crash reports scrubbed of all URL content.

**Accessibility.** All text meets WCAG AA. Verdicts never rely on colour alone. Touch
targets minimum 44px. Screen-reader labels on every control. Layout survives 200% text scale.

**Portability.** `lib/core/` imports no Flutter libraries and passes tests on the Dart VM.

## 8. UI/UX Requirements

All visual values come from `docs/design.md`. Never inline a colour, size, or radius.

**Home.** Headline, one-line privacy statement, URL input, primary "Scan this link"
button, dashed "Scan a QR code" button, history icon in the app bar.

**Scan.** Full-bleed camera preview, a centred reticle at `scan-reticle` size, torch
toggle, close control, and guidance copy. On decode, stop the stream immediately and
navigate to the result.

**Result.** Verdict badge, headline sentence, the scanned URL in monospace inside a
`url-display`, then either the clean-result explanation or a findings list. A closing
advice card for non-safe verdicts. No link affordance anywhere.

**History.** List of past scans, each showing a monospace URL and a compact verdict pill.
Swipe-to-delete, clear-all with confirmation, and an empty state stating that history is
local-only.

**Permission denied.** Explains why the camera is needed, offers a deep link to settings,
and keeps manual entry available.

## 11. Edge Cases & Error Handling

| Case | Behaviour |
|---|---|
| Camera permission denied | Explanatory state, settings deep link, manual entry still works |
| Permission permanently denied | Same, with copy directing to system settings |
| No camera on device | Hide the scan button; manual entry only |
| QR code won't decode | Keep scanning; after ~8s show "Try moving a little closer" |
| Decoded payload isn't a URL | Show decoded text marked "not a link — not scored" |
| Empty manual input | Inline validation, no navigation |
| Unparseable URL | Score 10, HIGH RISK, with a finding explaining it couldn't be read |
| Redirect wrapper self-reference | Recursion depth-capped at 3 |
| Corrupt history blob | Discard, render empty history |
| History at 50 items | Drop oldest on insert |
| Very long URL | Monospace block scrolls horizontally; layout never breaks |
| Device offline | No behaviour change — the scan path never needed the network |

## 14. Open Questions

1. ~~**Which OpenCV Flutter package?**~~ **Resolved 2026-09-07: `dartcv4` (v2.3.0).**
   `opencv_core` is discontinued and explicitly retired for Flutter 3.38+, which is the
   version in use — do not use it. `dartcv4` is the maintained successor, requires
   Dart 3.10 / Flutter 3.38+ (matches this project), ships prebuilt binaries for Android,
   iOS, Linux, Windows and macOS, and exposes the `objdetect` module containing the
   classical `QRCodeDetector` with `detectAndDecode`.
   **Use `objdetect.QRCodeDetector`, not the `wechat_qrcode` contrib module.** The WeChat
   detector is more robust but runs two pretrained CNN models, which would violate the
   "no pretrained ML in Layers 1-6" research constraint and invalidate the comparison the
   evaluation rests on. Note that `dartcv4` uses Native Assets / build hooks, so verify
   the Android and iOS release builds early.
2. ~~**`grambling.edu` scores 4 (SUSPICIOUS)**~~ **Resolved 2026-09-07 (TASK-038).**
   `gram` removed from the brand list; it was redundant with `grambling` and a substring
   of it. False positives fell 4.2% -> 2.4% across 212 legitimate URLs with zero change
   in detection across the 28-URL phishing corpus. Raising Rule 15's consonant threshold
   was evaluated and rejected — it gave no further false-positive reduction and downgraded
   `grarnbling.edu/student/login` from HIGH RISK to SUSPICIOUS. See `docs/evaluation.md`.

   **Still open (TASK-051):** five legitimate URLs remain at SUSPICIOUS via the same Rule 8
   failure mode — `outlook.office.com`, `login.microsoftonline.com`, `onedrive.live.com`,
   `gsumail.grambling.edu`. Rule 8 cannot tell that a large organisation legitimately hosts
   a brand on a differently-named apex. Fixing it needs either a brand-to-parent map
   (allowlisting, already a flagged methodological weakness) or a real notion of domain
   ownership — a research decision, not a patch.
3. **`arnazon.com` scores 0.** The prototype docstring claims LCS ≈ 0.86 catches it;
   actual is 0.714, under the 0.75 threshold. Correct the claim or lower the threshold —
   lowering it will raise false positives, so measure first.
4. **Homoglyph table contradicts its comment.** Code maps `7→b` and `8→t`; the comment
   says the reverse. One is wrong. The port preserved the code.
5. **Rule 21 fires on `javascript:alert(1)`** because `alert` is an urgency keyword,
   scoring 8 instead of 6. Harmless, but it shows Rule 21 matching scheme-body text.
6. **Should non-URL payloads be scored at all?** Currently out of scope, but a Wi-Fi
   join code or a payment payload carries real risk.
